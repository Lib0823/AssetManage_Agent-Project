# 시계열 데이터 TimescaleDB 마이그레이션

대용량 시계열 데이터 관리 효율·성능 개선 작업의 기록. 무엇이 문제였고, 어떤 방법으로 풀었고,
실제로 검증해보니 결과가 어땠는지를 가감 없이 남긴다. 성능 수치는 실측 그대로 적었고, 기대와
다르게 나온 부분도 숨기지 않았다.

## 1. 문제 정의

`ai-agent`가 평일 08:50마다 `stock_filter_score`(KOSPI 100 전체, 100행/일)를 비롯한 분석 결과를
매일 적재하고, `api-server`의 `MarketAnalysisRepository`는 이 테이블을 허브로
`prophet_forecast`/`news_analysis`/`stock_financial`/`ai_trade_decision`/`stock_realtime_price`를
LEFT JOIN해 화면에 필요한 데이터를 조립한다. 데이터가 몇 년치 누적되면 이 JOIN 비용이 계속
불어나는 구조다.

실측으로 먼저 확인한 것: 현재 쿼리는 대부분 **단일 날짜** 조회(`WHERE score_date = ?`)이고
`score_date`/`analysis_date`/`forecast_date`에 이미 인덱스가 있어서, "오늘 이미 심각하게
느리다"기보다는 **테이블이 계속 커지면 앞으로 심각해질 문제**에 가깝다. 반면
`asset_daily_snapshot`(자산 추이)과 `trade_history`(거래 이력)는 이미 실제 date-range 쿼리가
있다. 문제가 곪기 전에 미리 손보자는 방향이었다.

## 2. 대안 검토: MongoDB vs TimescaleDB

처음엔 MongoDB를 검토했다("NoSQL로 마이그레이션"이 기능 카드의 원안이었다). 검토 결과:

- **MongoDB**: 도큐먼트 모델이 `stock_news`(제목/본문/태그) 같은 데이터엔 잘 맞지만, 이 문제의
  핵심(JOIN 비용)을 풀려면 조인을 애플리케이션 레벨로 옮겨야 한다. 드라이버 이중화(Java+Python),
  이중 쓰기 기간, 정합성 재설계가 필요해 리스크가 크다.
- **TimescaleDB**: PostgreSQL 확장이라 SQL/JOIN/JPA/SQLAlchemy가 그대로 동작한다. 문제의
  본질(시계열 테이블이 커질수록 조회가 느려짐)을 정확히 겨냥한 해법(hypertable 자동
  파티셔닝 + chunk exclusion)이면서, 마이그레이션 리스크는 "테이블 선언 + `create_hypertable()`
  한 줄"에 가깝다.

**최종 선택: TimescaleDB.** "이슈에 대한 정확한 대응"을 우선했다 — NoSQL 전환 자체가 목적이
아니라 실제 문제(조인/쿼리 저하) 해결이 목적이므로, 엄밀히는 NoSQL이 아니지만 이 문제엔 더
적합한 도구를 선택했다.

## 3. 마이그레이션 대상 선정

| 우선순위 | 테이블 | 근거 |
|---|---|---|
| 1차 파일럿 | `asset_daily_snapshot` | 다른 테이블과 조인 없음, 볼륨 최소, 이미 date-range 쿼리 존재 — 리스크 최소로 패턴 검증 |
| 2차 (핵심) | `stock_filter_score` | `MarketAnalysisRepository`의 JOIN 허브, 매일 100행(Top30만이 아니라 KOSPI 100 전체) |
| 2차 | `prophet_forecast` | 매일 종목당 1행, D+1~D+5 예측 컬럼 15개 |
| 2차 | `news_analysis` | 매일 ~31행(종목 30 + 시장 1), `stock_code IS NULL` 시장 행 포함 |

**제외한 것들과 이유**
- `trade_history`/`trade_execution_plan`: 매매 원장 — TimescaleDB는 관계형을 유지하므로 ACID
  걱정 없이 hypertable화할 수 있지만, 이번 스코프에선 우선순위 밖으로 남겨뒀다.
- `stock_financial`: 분기 갱신이라 시계열 볼륨 문제 자체가 없음.
- `market_daily_summary`: 하루 1행, 마이그레이션 실익 없음.
- `stock_realtime_price`: writer가 없는 죽은 컬럼(항상 null) — 옮길 데이터가 없음.
- `stock_news`: 볼륨은 제일 크지만(최대 150행/일) 조인 허브가 아니라서 이번 스코프에서 뺐다.

## 4. 진행 중 만난 문제와 해결

### 4.1. `FATAL: extension "timescaledb" must be preloaded`
`postgres:16` → `timescale/timescaledb:latest-pg16` 이미지만 바꾸면 될 줄 알았는데, TimescaleDB는
Postgres 백그라운드 워커 훅을 쓰기 때문에 `shared_preload_libraries`에 서버 시작 전부터
등록돼 있어야 한다(`CREATE EXTENSION`만으론 부족). 새 볼륨이면 이미지의 초기화 스크립트가
자동으로 처리해주지만, **기존(구 `postgres:16`으로 초기화된) 볼륨을 재사용하면 이 스크립트가
다시 안 돈다.**

**해결**: `docker-compose.yml`에 `command: postgres -c shared_preload_libraries=timescaledb`를
명시. 새 볼륨이든 기존 볼륨이든 항상 동작한다.

### 4.2. hypertable의 PK 제약
TimescaleDB는 hypertable의 모든 PK/UNIQUE 제약이 파티션 컬럼을 포함해야 한다("uniqueness는
chunk 단위로 검사되므로"). 4개 대상 테이블 모두 `id BIGSERIAL PRIMARY KEY` 단독 PK였다.

**해결**: `dropPrimaryKey` → `addPrimaryKey(id, 날짜컬럼)` 복합키로 변경 후 `create_hypertable()`.
기존 `UNIQUE(stock_code, 날짜)`류 제약은 이미 파티션 컬럼을 포함해서 손대지 않았다. 이 레시피를
별도 테스트 컨테이너에서 5000행 데이터 + UNIQUE 위반 + UPDATE(JPA `save()` upsert 패턴) + FK
CASCADE DELETE + range 쿼리까지 전부 재현해서 확인한 뒤 실제 changeset을 작성했다.

이 PK 변경 때문에 api-server `AssetDailySnapshot` 엔티티에 `@IdClass` 복합키를 적용했다(이
테이블만 JPA로 매핑돼 있고, 나머지 3개는 `JdbcTemplate` native SQL로만 읽어서 Java 코드 변경이
필요 없었다).

### 4.3. `save_quantitative_features()` 청크 스캔 회귀 (마이그레이션이 유발한 진짜 버그)
`ai-agent/database/repository.py`의 `save_quantitative_features()`는 행을 로드해서 필드를
고치고 저장하는 방식이었다. SQLAlchemy ORM은 이걸 `WHERE id = ..` 단독 조건의 UPDATE로
번역하는데, hypertable 전환 후 EXPLAIN으로 확인하니 **이 UPDATE가 모든 chunk에 index scan을
거는 13-way fan-out**이 되어 있었다(청크는 연 ~52개씩 증가하는 추세). 마이그레이션의 목적
(조회 성능 개선)을 이 한 경로에서 정반대로 만들 뻔한 지점이었다.

**해결**: 행을 로드하지 않고 `session.query(StockFilterScore).filter(stock_code=.., score_date=..).update({...})`로
바꿔서 `score_date`가 WHERE에 남게 했다. 이제 단일 chunk로 배제된다. Stage 2-1에서 종목당 1회
(하루 ~30회) 호출되는 경로다.

```diff
- record = session.query(StockFilterScore).filter(stock_code=.., score_date=..).first()
- record.morning_return = morning_return
- record.close_position = close_position
- session.commit()
+ updated = session.query(StockFilterScore).filter(stock_code=.., score_date=..).update(
+     {StockFilterScore.morning_return: morning_return, StockFilterScore.close_position: close_position},
+     synchronize_session=False)
+ session.commit()  # updated 가 0 이면 rollback
```

**`StockFilterScore` 모델 자체는 안 고쳤다.** `score_date`를 SQLAlchemy 모델에도
`primary_key=True`로 추가해봤지만 (a) SQLite 테스트 대역이 `CompileError: SQLite does not
support autoincrement for composite primary keys`로 깨졌고 (b) 실측 확인 결과 ORM PK가 DB PK의
부분집합이어도 SQLAlchemy가 만드는 WHERE는 필요한 것보다 넓을 뿐 틀리지 않아서(그리고 `id`가
시퀀스라 전역 유일해서 오매칭도 없음) 실제로 문제가 없었다. 테스트 대역을 갈아엎을 이득이
없어 원복했다. `ProphetForecast` 모델은 애초에 `id`를 매핑조차 안 하고
`(stock_code, forecast_date)`만 쓰므로 영향 없다. `news_analysis`는 SQLAlchemy ORM 클래스
자체가 없고 raw SQL(`DELETE`+`INSERT`, `ON CONFLICT (stock_code, analysis_date) DO UPDATE`)로만
쓴다.

### 4.4. 벤치마크 합성 데이터 버그
성능 실측 초반에 날짜 생성 SQL(`generate_series` + 정수 나눗셈 조합)이 잘못돼 33년치로
쪼개진 비현실적 데이터가 만들어졌다. chunk당 표본이 너무 적어(~100행) 압축률이 나쁘게
나왔는데, 이게 TimescaleDB의 한계인지 내 데이터 생성 버그인지 구분이 안 됐다. 실제 서비스
패턴(평일만, 5~7년치, 종목 100개)으로 다시 만들어서 재측정했다 — 아래 [6장](#6-성능-실측) 결과는
이 수정된 데이터 기준이다.

## 5. 검증 (TDD)

Docker(Testcontainers, `timescale/timescaledb:latest-pg16`)에 **실제 프로덕션 Liquibase
changelog**(`db.changelog-master.yaml`, v1.0~v1.24)를 그대로 적용해 "이 changelog가 처음부터
끝까지 깨끗하게 적용되는가"부터 검증한다. `api-server/src/test/java/.../migration/`에
17개 테스트:

| 파일 | 검증 항목 |
|---|---|
| `AssetDailySnapshotHypertableMigrationTest` (8개) | hypertable 등록, PK 형태, UNIQUE/FK 제약, upsert(find-then-update) 패턴, CASCADE 삭제, date-range 쿼리 |
| `AnalysisTablesHypertableMigrationTest` (5개) | 3개 테이블 hypertable 등록, UNIQUE 제약, ai-agent의 DELETE-then-INSERT 재적재 패턴, **실제 3중 LEFT JOIN 쿼리**(sfs+news+prophet) 정확성, chunk exclusion |
| `MarketAnalysisRealRepositoryHypertableTest` (4개) | **`MarketAnalysisRepository`/`MarketAnalysisService` 실클래스**를 그대로 생성해 `getHeatmapData()`/`getStockAnalysis()`/`getStockDetailAnalysis()` 실호출 — 손으로 옮겨 적은 재현 SQL이 아니라 진짜 프로덕션 코드 경로 검증 |

Docker가 필요해 기본 `./gradlew test`에서는 제외되고 `./gradlew timescaledbTest`로 별도
실행한다(JUnit5 `@Tag("timescaledb")` + Gradle 태스크 분리).

ai-agent 쪽은 실제 dev DB(마이그레이션 적용 완료 상태)에 `DatabaseRepository`를 직접 붙여
23개 항목(저장→재조회 값 일치, 동일 날짜 재실행 멱등성, prophet 재실행 시 1행 유지, news_analysis
`ON CONFLICT` upsert 등)을 검증했고, 이어서 `ON CONFLICT` 경로만 따로 12개 항목 더 검증했다 —
`EXPLAIN`으로 `Conflict Arbiter Indexes: news_analysis_stock_code_analysis_date_key`가 정확히
잡히는 것, 즉 새 복합 PK가 conflict arbiter를 가로채지 않는 것까지 확인했다.

기존 테스트 전부 회귀 없음: api-server 491개, ai-agent 740개.

## 6. 성능 실측

### 6.1. 1차 실측 (18만행) — 규모가 작아서 판단이 어려웠다

별도 컨테이너에 평일만·7년치·종목 100개(182,700행)로 동일 데이터를 일반 테이블/hypertable
양쪽에 적재하고 비교했다. 결과: 점 조회는 hypertable이 빨랐지만(0.035ms vs 0.133ms) 둘 다
서브밀리초라 체감 차이가 없었고, range 조회는 plan 비용이 오히려 hypertable 쪽이 컸다(14.7ms
vs 0.5ms). 이 규모에서는 Postgres 기본 B-tree가 이미 충분히 빨라서 판단을 내리기엔 데이터가
작았다 — 그래서 훨씬 큰 규모로 다시 측정했다.

### 6.2. 2차 실측 (261만행) — 실제로 유의미한 격차가 나오는 지점까지 키움

**방법**: 평일만·10년치(2015-08~2025-08)·종목 1,000개(멀티마켓 확장 시나리오 가정) =
**2,610,000행**을 동일하게 적재(일반 테이블 451MB, hypertable 523개 chunk). 점 조회/range
집계/데이터 정리(retention)/압축 4가지 시나리오로 나눠 측정했다.

| 시나리오 | 일반 테이블 | hypertable | 결과 |
|---|---|---|---|
| **점 조회** (최근 1일, `WHERE score_date=? AND is_selected`) | 0.406ms, buffer 17 | 0.096ms, buffer 7 | **hypertable 4.2배 빠름** |
| **range 집계 — 최근 30일** | 9.68ms | 17.7ms (7일 chunk) / 17.1ms (30일 chunk 튜닝) | **일반 테이블이 1.8배 빠름** — chunk 간 Partial/Finalize Aggregate 조율 비용 |
| **range 집계 — 1년치** | 54.5ms | 146.8ms (7일 chunk, plan 21.9ms) / 70.8ms (30일 chunk 튜닝) | **일반 테이블이 1.3~2.7배 빠름** — chunk 튜닝해도 못 따라잡음 |
| **오래된 데이터 정리** (30% = 78.2만행 삭제) | `DELETE` 462ms + `VACUUM FULL` **5,251ms**(전체 테이블 배타 락) = 총 **~5.7초** | `drop_chunks()` **202ms**, 락 없음, 남은 chunk 무영향 | **hypertable 28배 빠르고 무중단** |
| **압축** (30일 chunk 튜닝 후) | 295MB (VACUUM 후) | 486MB → 압축 후 **197MB** | **hypertable이 압축 후 33% 더 작음** |

**솔직한 결론 — 쿼리 모양에 따라 승자가 다르다**:
- **현재 코드가 실제로 쓰는 패턴**(`MarketAnalysisRepository`의 단일 날짜 점 조회 + JOIN)에는
  hypertable이 명확히 유리하다(4배, buffer 절반 이하).
- **넓은 날짜 범위를 GROUP BY로 집계하는 쿼리**(예: "1년 추이")는 오히려 hypertable이
  느리다 — chunk마다 부분 집계를 만들고 다시 합치는 조율 비용 때문이다. `chunk_time_interval`을
  기본 7일에서 30일로 튜닝하면 격차가 절반 가까이 줄지만(146.8ms→70.8ms) 완전히 따라잡지는
  못했다. **지금 코드베이스엔 이런 쿼리가 없어서 당장 문제는 아니지만, 향후 "연간 추이 차트"
  같은 기능을 추가한다면 이 트레이드오프를 알고 설계해야 한다.**
- **가장 극적이고 확실한 승리는 데이터 정리(retention)다** — `DELETE`는 죽은 튜플만 남기고
  실제 디스크는 안 줄어들어서 `VACUUM FULL`(5.2초, 그동안 테이블 전체 배타 락)이 따로
  필요하지만, `drop_chunks()`는 물리적으로 chunk 파일을 지우는 거라 202ms면 끝나고 다른
  chunk·다른 쿼리에 전혀 영향을 안 준다. **이 프로젝트처럼 데이터가 평생 쌓이기만 하는
  시스템에서, 언젠가 "N년 지난 데이터는 정리"하게 될 때 이 차이가 가장 크게 체감될 것이다.**
- **압축은 chunk당 표본 수에 민감하다** — 1차 실측(7일 chunk, chunk당 ~5행/종목)에선 압축이
  오히려 용량을 늘렸지만, 2차 실측(30일 chunk, chunk당 ~22행/종목)에선 33% 절감했다. 압축을
  쓰려면 chunk 크기를 데이터 밀도에 맞게 튜닝해야 한다는 뜻이다.

### 6.3. range 집계가 왜 느린지, 그리고 그게 우리 서비스 패턴이 맞는지 재확인

**왜 느린가**: `GROUP BY` 집계 쿼리가 여러 chunk에 걸치면 Postgres는 각 chunk마다 부분 집계
(`Partial HashAggregate`)를 따로 계산하고, 이를 다시 합치는(`Finalize HashAggregate`) 단계를
거친다. 1년치 쿼리가 52개 chunk를 건드리면 52번의 부분 집계 + 병합 오버헤드가 붙는다. 게다가
이 시나리오는 조회 범위 안의 chunk를 전부 건드려야 해서(제외되는 chunk가 없어서) 파티셔닝의
이득(chunk exclusion)은 못 받고 "나눠서 계산 후 합치는" 비용만 지불한다.

**그런데 이게 우리 서비스가 실제로 쓰는 패턴인가 — 재확인해보니 아니었다.** 이 프로젝트에
실제로 존재하는 range 쿼리는 `asset_daily_snapshot.getHistory()`
(`findByUserIdAndSnapshotDateBetweenOrderBySnapshotDateAsc`) 하나뿐인데, 이건 **`GROUP BY`
없는 단순 `SELECT ... WHERE user_id=? AND date BETWEEN ? AND ? ORDER BY date`**다. 위 6.2의
"range 집계" 테스트는 "나중에 연간 추이 기능이 생기면 어떨까"를 가정한 탐색적 테스트였지 실제
코드를 재현한 게 아니었다.

그래서 **진짜 쿼리 형태(GROUP BY 없이)를 1,000명 사용자 × 10년치(365만 4천행) 규모로 다시
측정**했다:

| | 일반 테이블 | hypertable |
|---|---|---|
| 실제 `getHistory()` 형태 (1년 범위, 특정 user_id, ORDER BY, GROUP BY 없음) | 2.348ms | 2.373ms |

**사실상 동일하다(1% 차이, 오차범위 안).** GROUP BY가 없으니 부분집계/병합 오버헤드 자체가
없고, hypertable은 `ChunkAppend`로 관련 chunk의 결과를 순서대로 이어붙이기만 한다(정렬도
chunk가 이미 날짜순이라 별도 소트 없이 자연스럽게 됨). **즉 6.2의 "range 집계가 느리다"는
결과는 지금 코드에 없는 가상의 쿼리 패턴(GROUP BY 집계)에서만 나타나고, 실제로 존재하는 range
쿼리 패턴에서는 아무 역효과가 없다.**

**"90% 개선" 문구에 대한 정직한 평가**: 어떤 쿼리를 기준으로 잡느냐에 따라 완전히 다른 숫자가
나온다. 점 조회는 4배(75% 단축), retention은 28배(96% 단축)로 90%를 넘고, 실제로 존재하는
range 쿼리(비집계)는 개선도 손해도 없이 동일하다. **아직 코드에 없는 GROUP BY 집계 패턴만
오히려 나빠지며, 이는 지금 서비스가 실제로 쓰는 패턴이 아니다.** 하나의 숫자로 "90%
개선됐다"고 말하는 건 정직하지 않지만, "지금 코드가 실제로 쓰는 모든 쿼리 패턴(점 조회+JOIN,
비집계 range 조회)에서 개선되거나 최소한 손해가 없고, 데이터 정리는 극적으로 개선된다"는
근거 있는 결론은 낼 수 있다.

## 7. 최종 결과

- **전환 완료**: `asset_daily_snapshot`, `stock_filter_score`, `prophet_forecast`,
  `news_analysis` — 4개 테이블
- **데이터 무결성**: 실 dev DB에 적용 후 데이터 손실 없음 확인(`stock_filter_score` 527행 그대로,
  전후 chunk 수·행 수 동일)
- **정합성**: UNIQUE/FK 제약, upsert/`ON CONFLICT` 패턴, JPA `@IdClass` 복합키, ai-agent
  ORM/raw SQL 쓰기 경로 전부 실측 검증 통과
- **프로덕션 코드 경로 검증**: `MarketAnalysisRepository`/`MarketAnalysisService` 실클래스를
  Testcontainers에 붙여 `getHeatmapData()`/`getStockAnalysis()`/`getStockDetailAnalysis()` 직접
  호출 검증 (손으로 옮긴 재현 SQL이 아니라 진짜 프로덕션 코드)
- **회귀**: 1건 발견·수정(`save_quantitative_features`)
- **테스트**: 신규 17개(Testcontainers) + 기존 491개(api-server) + 740개(ai-agent) 전부 통과
- **성능 (261만행 + 365만행 실측)**: 현재 코드가 실제로 쓰는 모든 패턴(점 조회+JOIN, 비집계
  range 조회)에서 개선되거나 최소 동일함을 확인 — 점 조회 **4배**(buffer 기준 2.4배), 실제
  `getHistory()` range 조회는 오차범위 내 동일(2.35ms vs 2.37ms), 오래된 데이터 정리는

  느림(실사용 패턴 아님) — "90% 개선"은 쿼리 종류에 따라 다르며 일괄 적용되는 수치는 아니지만,
  실제 사용 패턴 기준으로는 손해 보는 경로가 없다

## 8. 향후 과제

- **실제 프로덕션 데이터로 재측정**: 261만행 벤치마크는 합성 데이터다. 실제 매일 적재가 쌓여
  비슷한 규모(수년치)에 도달하면 동일 시나리오(점 조회/range 집계/retention/압축)로 다시
  측정해 합성 데이터 결과와 실제가 얼마나 일치하는지 확인해야 한다.
- **`chunk_time_interval` 튜닝**: 261만행 실측에서 기본값(7일)은 1년치 range 집계에서 plan
  비용만 21.9ms가 나올 정도로 chunk가 과도하게 잘게 쪼개졌다. 30일로 늘리면 실행시간이
  거의 절반(146.8ms→70.8ms)으로 줄었다 — 실제 운영 전에 이 값을 30일 안팎으로 조정하는 걸
  권장한다. 다만 이 프로젝트가 하루 100행씩 밖에 안 쌓이는 걸 감안하면 90일 이상도 고려할
  만하다.
- **넓은 범위 GROUP BY 집계 쿼리 설계 시 주의**: "연간 추이" 같은 기능을 추가한다면, chunk
  튜닝만으로는 일반 테이블 대비 확실히 빠르다고 보장할 수 없다는 걸 실측으로 확인했다.
  이런 쿼리가 자주 필요해지면 TimescaleDB의 **continuous aggregate**(증분 갱신 materialized
  view)로 사전 집계해두는 걸 검토해야 한다 — 매번 여러 chunk를 훑어 부분집계를 조율하는
  대신 미리 계산된 결과를 읽게 된다.
- **데이터 정리(retention) 정책 도입**: 실측에서 가장 확실한 이득(28배, 무중단)이 나온
  영역이니, "N년 지난 데이터는 자동 정리" 같은 정책이 생기면 `drop_chunks()` 기반으로
  구현하는 게 명백히 유리하다.
- **압축 정책 적용**: `compress_segmentby`/`compress_orderby`를 chunk 크기(30일 튜닝 기준)에
  맞춰 실 데이터에 설정하면 실측상 33% 절감 효과가 있었다. 이를 자동 압축 정책
  (`add_compression_policy`)으로 등록하는 것도 검토.
- **압축 정책 재검토**: 이번 실측에서 압축이 역효과였던 건 합성 데이터 특성 때문일 가능성이 크다
  (진짜 수급/스코어 데이터는 무작위보다 패턴이 있을 수 있음). 실 데이터가 충분히 쌓이면
  `compress_segmentby`/`orderby` 조합을 다시 실측해서 결정.
- **`stock_news` 전환 검토**: 볼륨은 제일 크지만(150행/일) 조인 허브가 아니라 이번 스코프에서
  뺐다. 뉴스 화면 조회가 느려지면 재검토.
- **`trade_history` hypertable화 검토**: TimescaleDB는 관계형을 유지하므로 ACID 문제 없이
  가능하다. 거래 이력이 충분히 쌓이면 후속 작업으로 고려.
