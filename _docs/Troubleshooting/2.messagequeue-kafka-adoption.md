# 매매 실행 신뢰성 개선: Kafka 메시지 큐 도입

분석 파이프라인(ai-agent)과 매매 실행(api-server) 사이의 결합을 비동기 큐로 바꾼 작업의 기록. 처음
가설이 코드로 확인해보니 틀렸던 과정, 실제로 값을 하는 지점만 추려 좁힌 이유, 구현 중 테스트가
스스로 거짓 통과를 만들어낸 사고와 그걸 잡아낸 과정, 그리고 검증에서 실제로 새 버그를 하나 찾아
고친 과정까지 가감 없이 남긴다.

## 1. 문제 정의

시작은 "분석 파이프라인이 API 서버와 동기적으로 실행되어 API 서버 스레드가 장시간 점유되고,
데이터 수집 단계 실패 시 전체 트랜잭션이 중단된다"는 가설이었다. Kafka를 Producer(분석 요청)/
Consumer(실행) 분리에 쓰면 해결될 거라 생각했다.

**코드로 확인한 결과 이 가설은 틀렸다.** `api-server` 전체를 검색해도 ai-agent를 호출하는 코드가
한 줄도 없었다 — 호출 방향은 정반대로, ai-agent(FastAPI)가 api-server를 호출한다. Stage 0~6
분석 파이프라인은 전부 ai-agent 프로세스 내부에서 APScheduler로 돌고, api-server 스레드는 이
파이프라인과 무관하다.

대신 코드 조사로 실제로 존재하는 문제 두 가지를 찾았다.

**이슈 1 — 매매 주문 유실.** ai-agent Stage 6이 `POST /api/internal/users/{userId}/trades/{buy|sell}`를
aiohttp로 동기 호출하는데, 실패 시 재시도가 전혀 없었다. api-server가 다운돼 있거나 KIS가
타임아웃되면 그 주문은 영구히 사라지고, 파이프라인 자체는 "성공"으로 마감됐다. 게다가
`TradingService.executeBuy/executeSell`는 `trade_history` 테이블에 아무것도 쓰지 않아서
(`TradeHistoryRepository`의 유일한 사용처가 읽기 하나뿐) `GET /api/trading/recent`가 항상 빈
배열을 반환하고 있었다 — 매매 감사 로그가 시스템 어디에도 없었다.

**이슈 2 — 파이프라인 동시 실행 방지 부재.** 평일 08:50 스케줄 트리거와 `POST /api/pipeline/trigger`
수동 트리거가 각각 독립적으로 `PipelineOrchestrator`를 실행할 수 있는데, 동시 실행을 막는 락이
전혀 없었다. 겹치면 같은 날짜 행을 중복 DELETE 후 재삽입하고, 최악의 경우 동일 유저에게 중복
매수 주문이 나갈 수 있었다.

## 2. 범위 확정: 왜 이 2건만인가

조사 과정에서 Kafka 후보 지점을 5개까지 넓혀봤다(주문 유실, 파이프라인 동시성, Gemini RPM
큐잉, 종목 단위 수집 재시도, Stage 경계 체크포인트). 하지만:

- **종목 단위 수집 재시도**는 KIS 5req/s 전역 제한이 그대로라 처리량 이득이 없고 관측성 이득뿐이었다.
- **Stage 경계 체크포인트**는 780줄 단일 함수가 DataFrame을 지역변수로 넘기는 구조라, 적용하려면
  DB 재조회 기반 리팩터링이 선행돼야 했다. 공사 규모가 이번 스코프를 압도했다.
- **Gemini 결정 큐잉**은 당일 컷오프 정책(큐가 밀렸을 때 그날 실행을 포기할지, 언제까지
  기다릴지)이 아직 정해지지 않은 상태였다. 정책 없이 큐부터 만들면 "밀린 요청이 계속 쌓이기만
  하는" 구조가 될 위험이 있어 제외했다.

그래서 **설계가 확정돼 있고 검증 가능한 범위**인 이슈 1·2만 이번에 구현했다. 두 이슈는 우연히도
서로를 보강한다 — 이슈 1의 멱등키가 이슈 2의 잔여 리스크(파이프라인 중복 실행 시 중복 주문)를
막아주는 안전망 역할도 한다. 이 관계는 [7장](#7-실측-결과)에서 실측으로 확인한다.

## 3. 메시지 계약 설계

두 모듈을 각각 독립적으로 작업하는 담당자(backend-engineer, ai-pipeline-engineer)에게 고정
스펙으로 전달했다 — 경계면 드리프트를 실시간 조율 없이도 막기 위해서다.

| 토픽 | 발행 | 소비 | 용도 |
|---|---|---|---|
| `trade.order.requested` | ai-agent | api-server | 주문 요청. key = `{userId}:{stockCode}:{tradeDate}:{side}`(멱등키) |
| `trade.order.result` | api-server | ai-agent | 처리 결과(`SUCCESS`\|`FAILED`) |
| `trade.order.dlq` | api-server | (사람이 수동 확인) | 재시도 소진/재시도 불가 주문 격리 |
| `pipeline.run.requested` | ai-agent(스케줄+수동) | ai-agent(단일 컨슈머) | 트리거 직렬화 |

메시지 본문은 8개 필드(`idempotencyKey`, `userId`, `stockCode`, `side`, `quantity`, `price`,
`tradeDate`, `requestedAt`)로 고정했고, 멱등키는 record key와 body 양쪽에 모두 채우도록 지시했다
(컨슈머가 어느 쪽을 읽어도 안전하게).

## 4. 구현

### 4.1 api-server — 컨슈머, 멱등성, DLQ

**PENDING 선(先) claim 채택.** KIS 호출 *후*에만 결과를 기록하면, 주문 직후 프로세스가 죽었을 때
흔적이 안 남아 재전달 시 이미 나간 주문을 또 낼 위험이 있다. 그래서 KIS 호출 **전에** PENDING
행을 INSERT하고 즉시 커밋(`REQUIRES_NEW`)한다. 행의 **존재 자체**가 재실행을 막는 방어선이고,
최종 방어선은 `trade_history.idempotency_key` UNIQUE 제약이다(조회 기반 체크만으론 TOCTOU로
뚫린다). Liquibase `v1.25-trade-history-idempotency.yaml`로 `idempotency_key VARCHAR(120)`
(NULL 허용) + UNIQUE 제약을 추가했다 — NULL을 허용한 게 핵심으로, 기존 행과 비-Kafka 경로(수동
주문/REST)는 이 제약에 걸리지 않는다.

**재시도 경계는 예외 타입이 아니라 "KIS를 호출했는가"라는 단계(phase) 기준.** 처음엔 예외
타입으로 구분하려 했으나, `KisApiClient.callKisApi`가 네트워크 타임아웃(`ResourceAccessException`)
마저 `KisApiException.networkError`로 감싸서 던지는 걸 발견했다 — "도달 불확실 실패"와 "KIS
명시적 거부"가 코드베이스에서 이미 같은 예외 타입으로 올라오고 있었다. 그래서 컨슈머 로직을
3단계로 나눴다:

- **PHASE 0**(메시지 파싱)·**PHASE 2**(KIS 호출 전/후) 예외는 **삼켜서** 재전달을 원천 차단한다.
  시장가 주문에서 타임아웃은 "안 들어갔다"가 아니라 "들어갔는지 모른다"는 뜻이므로, 이 구간의
  실패는 무조건 즉시 FAILED 확정 + DLQ 격리다.
- **PHASE 1**(DB 커넥션 등 KIS를 아직 안 건드린 인프라 오류)만 일부러 다시 던져 Spring Kafka의
  `DefaultErrorHandler` + `ExponentialBackOff`(초기 2초, 배수 2, 최대 3회)가 재시도하게 한다.
  소진되면 커스텀 `ConsumerRecordRecoverer`가 `trade.order.dlq`로 보낸다
  (`DeadLetterPublishingRecoverer` 기본 구현은 `<topic>.DLT` + 헤더 기반이라, "고정 토픽명 +
  본문 필드"라는 계약과 안 맞아 직접 구현했다).

**Kafka JSON serde를 String으로 고정.** spring-kafka 4.1은 Jackson 2를, Spring Boot 4.1은
Jackson 3을 쓰는 걸 확인했다. 둘이 공존한 상태로 `JsonSerializer`를 그대로 쓰면 직렬화 포맷이
갈릴 위험이 있어, JSON 매핑을 코덱 한 곳으로 모아 String serde로 통일했다.

### 4.2 ai-agent — 프로듀서/컨슈머, 파이프라인 직렬화

**`messaging/` 패키지 신설.** `pipeline`과 `execution` 양쪽이 이 모듈을 쓰므로 독립 패키지로
뺐다. 기존 `internal_api_client.py`(REST 클라이언트)는 삭제하지 않고 남겨뒀다 — 디버깅/수동
실행 경로로 여전히 쓰인다.

**결과 수신을 위한 상태 매핑.** 결과 메시지의 `status: "SUCCESS"|"FAILED"`는 와이어 계약
그대로 유지하되, ai-agent 자신의 `trade_execution_plan.execution_status` 컬럼에는
`RESULT_STATUS_TO_DB` 매핑을 거쳐 `EXECUTED`로 저장한다. 기존 뷰 `v_latest_trade_plan`
(v1.6)과 `v_market_overview`(v1.7)가 `execution_status = 'EXECUTED'`로 체결 건수를 세고
있어서, `SUCCESS`를 그대로 넣으면 대시보드 집계가 조용히 0이 되기 때문이다. 원문 status는
`execution_result` JSONB에 그대로 보존해뒀다.

**파이프라인 직렬화**는 스케줄·수동 트리거 둘 다 `PipelineOrchestrator`를 직접 호출하지 않고
`pipeline.run.requested`(key=trade_date, 파티션 1개)에 발행하도록 바꿨다. 단일 컨슈머가 이
토픽을 순차 소비해 실제 `run_complete_pipeline()`을 실행한다. 수동 트리거 엔드포인트는 발행 직후
즉시 202를 반환한다(이전엔 파이프라인 전체가 끝날 때까지 동기 대기).

`main.py`의 FastAPI lifespan에 프로듀서 초기화 + 결과 컨슈머 + 파이프라인 컨슈머 백그라운드
태스크를 추가했고, 종료 시 producer flush/close + consumer task cancel까지 정리한다.

## 5. 진행 중 만난 문제와 해결

### 5.1 뮤테이션 테스트가 잡아낸 거짓 통과 (가장 중요한 발견)

api-server 컨슈머의 "PHASE 2는 재시도 금지" 규칙을 검증하려고, 일부러 PHASE 2에 rethrow를
주입하는 뮤테이션 테스트를 돌렸다. **그런데 테스트가 그대로 통과했다.** 원인은 두 가지였다.

1. 재전달이 실제로 일어나도, 멱등성 계층이 걸러서 KIS 호출 횟수는 여전히 1회로 유지됐다 —
   즉 `times(1)` 단언이 "재시도 안 함"이 아니라 "멱등성이 작동함"을 검증하고 있었다.
2. DLQ 발행이 rethrow보다 **먼저** 일어나서, 재전달이 실제로 오기 전(200ms 뒤)에 테스트가 이미
   끝나버리는 **타이밍 레이스**였다.

재전달 자체를 직접 관측하도록(`claim` 호출 횟수 + DLQ 건수) 단언을 바꾸고 2초 정착 대기를
추가한 뒤 뮤테이션을 재적용하니 `TooManyActualInvocations`로 정상 실패했고, 되돌리니 다시
통과했다. **테스트가 통과한다는 사실 자체가 검증이 아니라는 걸 재확인한 사례.**

### 5.2 `date.fromisoformat`이 조용히 성공한 사례

ai-agent 쪽 "잘못된 날짜" 테스트가 `'20260809'`(구분자 없는 형식)를 잘못된 입력으로 기대했는데,
Python 3.11의 `date.fromisoformat`은 ISO basic format도 지원해서 **그대로 파싱에 성공**했다.
테스트가 거짓으로 통과하고 있던 걸 발견해 `'2026-13-45'`(범위를 벗어난 실제 무효값)로 교체하고,
이 동작 자체를 별도 테스트로 문서화했다.

### 5.3 Stage 6 발행-INSERT 순서 레이스 (경계면 QA가 찾아낸 실제 버그)

경계면 교차 검증([8장](#8-경계면-교차-검증)) 과정에서 발견했다. 원래 구현은 유저별로
"① Kafka 발행 → ② 발행 결과 기반 레코드 생성 → ③ `trade_execution_plan` 일괄 INSERT"
순서였다. api-server가 KIS를 아예 호출하지 않고 즉시 실패를 반환하는 초고속 경로(계약 위반
메시지, DB claim 실패 등)에서는 결과가 ③번 INSERT보다 먼저 도착할 수 있었다 — 그러면 결과
컨슈머의 UPDATE가 0행을 갱신하고(경고만 남기고 끝), 뒤이은 ③번 배치 INSERT가 그 행을
`QUEUED`로 (재)생성해버려 **이미 확정된 실패가 영구히 QUEUED로 남는** 문제였다.

불변식을 "행이 존재하는 시점 < 결과가 도착할 수 있는 시점"으로 뒤집어 고쳤다:
"① 주문 목록만으로 초기 레코드 생성(QUEUED) → ② `trade_execution_plan` 일괄 INSERT → ③ 그
다음에 Kafka 발행 → ④ 발행 자체가 실패한 주문만 단건 UPDATE로 FAILED 처리". 초기 상태를
`PENDING`이 아니라 처음부터 `QUEUED`로 심은 게 핵심 판단이었다 — PENDING으로 심고 발행 성공 시
QUEUED로 승격하는 방식은 그 승격 UPDATE가 이미 도착한 결과를 되돌려 **같은 레이스를 재발**시킨다.
QUEUED로 바로 심으면 발행 성공 경로엔 추가 UPDATE가 아예 없어 결과를 되돌릴 경로 자체가 없다.

레이스를 실제로 재현하는 테스트 5개(`TestFastResultRace`)를 작성해 수정 전 전부 실패, 수정 후
전부 통과하는 걸 확인했다(5절 상세는 [6장](#6-검증-tdd) 참고).

## 6. 검증 (TDD)

`1.timescaledb-migration.md`와 동일한 기준을 따랐다 — Testcontainers로 실제 인프라(Kafka +
PostgreSQL)를 띄워 프로덕션 코드 경로를 그대로 검증했다.

### api-server (`kafkaTest` 태그, Docker 필요해 기본 `test`에서 분리)

실제 PostgreSQL(TimescaleDB)+Kafka(`apache/kafka:4.0.0`, KRaft) 컨테이너에 전체 Liquibase
changelog(v1.0~v1.25)를 적용, KIS 클라이언트만 목으로 대체.

| 테스트 | 검증 항목 | 결과 |
|---|---|---|
| 정상 매수/매도 주문 | `EXECUTED` 기록 + result `SUCCESS` 발행 | PASS |
| 동일 키 3회 발행 | KIS 호출이 **정확히 1번**만 일어남(멱등성) | PASS |
| KIS 타임아웃 | 재시도 없이 즉시 DLQ(claim 1회, retryCount:0) | PASS |
| KIS 비즈니스 오류(4xx) | 재시도 없이 즉시 DLQ | PASS |
| 인프라 레벨 일시 오류 | claim 4회(최초1+재시도3), retryCount:3, **KIS 호출 0회** | PASS |
| 계약 위반 메시지 | DLQ 격리, KIS 0회 | PASS |

## 7. 실측 결과

### 7.1 트리거 응답 시간

가짜 파이프라인(2,000ms 시뮬레이션) 기준, 수동 트리거 3회 실측:

| 상황 | 응답 시간 |
|---|---|
| 유휴 시 트리거 | 32.4ms / 3.6ms / 3.9ms |
| **파이프라인 실행 중** 트리거 | **13.6ms / 7.6ms / 10.8ms** |

이전엔 파이프라인 전체(수십 분)가 끝날 때까지 동기 대기했던 것과 비교하면, 발행 후 즉시 응답하는
구조로 확실히 바뀌었다.

### 7.2 파이프라인 직렬화

`_job_wrapper()`를 실제 별도 스레드에서 호출하며 동시에 HTTP로 수동 트리거를 걸어 측정:

```
run2 시작 - run1 종료 = +0.028s / +0.008s / +0.005s   (3연발 반복 동일)
최대 동시 실행 수 = 1 (한 번도 2가 된 적 없음)
```

항상 양수 — 겹치지 않고 순차 실행됨을 확인했다. 두 요청 모두 **유실 없이** 큐에 쌓여 실행됐다
(하나를 버리는 게 아니라 순서대로 처리).

### 7.3 멱등성이 파이프라인 중복 실행의 잔여 리스크를 막아주는가

2장에서 세운 가설("이슈 1의 멱등키가 이슈 2의 잔여 리스크도 막아준다")을 실측했다.
**ai-agent 단독으로는 막지 못한다 — api-server의 dedup이 있어야 성립한다.** 같은 거래일로
파이프라인을 두 번 실행하면 ai-agent는 스스로 걸러내지 않고 메시지 **2건**을 발행한다(두 키는
완전히 동일). 그 2건을 mock 컨슈머로 받아 dedup을 적용하면 실행은 **1건**으로 줄어든다 — 즉
"분석 단계는 중복으로 돌아도, 실제 주문은 한 번만 나간다"는 원래 설계 의도가 **api-server의
멱등성 계층 존재를 전제로** 성립한다. 한쪽만 있으면 안 되고 둘 다 필요하다.

**한계도 실측으로 확인했다**: 멱등키에 수량이 없다. 재실행 사이에 계획 수량이 10주→50주로
바뀌어도 먼저 도착한 10주 요청이 이긴다(의도된 트레이드오프 — 나중에 온 걸 우선하면 어느 쪽이
"최신"인지 판단할 근거가 메시지 자체엔 없다).

## 8. 경계면 교차 검증

두 담당자가 독립적으로 구현했으므로, 실제로 같은 메시지 포맷을 주고받는지 정적 대조로
확인했다(별도 integration-qa 에이전트). ai-agent의 실제 직렬화 코드를 실행해 나온 바이트를
api-server DTO/테스트 픽스처와 직접 비교하는 방식으로, end-to-end 실측 다음으로 강한 검증이다.

**7개 계약 항목 전부 일치, 불일치 0건**:

1. `idempotencyKey`가 record key와 body 양쪽에 모두 채워짐 (body 누락 위험 없음)
2. 멱등키 조합 규칙 — api-server가 키를 재조립하지 않고 받은 문자열을 그대로 저장/반환하므로
   구조적으로 드리프트 여지가 없음
3. JSON 필드명 camelCase 통일 (Java `@JsonIgnoreProperties(ignoreUnknown = true)`로 향후 필드
   추가에도 안전)
4. `status` 값은 wire 상 그대로 유지되고, `EXECUTED` 매핑은 ai-agent DB 저장 시점에만 적용됨
5. `price`/`quantity` 타입 — Python int → Java `Integer`/`BigDecimal`, 시장가 `price=0`의 의미도
   양쪽에서 동일(매수여력 조회 스킵 + `ORD_DVSN="01"`)
6. 타임스탬프 — `requestedAt`은 오프셋 포함 ISO-8601로 양쪽 파싱 가능, `processedAt`은 ai-agent가
   애초에 파싱하지 않고 불투명 문자열로만 다뤄 포맷 드리프트 위험 자체가 없음
7. 토픽 이름 — 점 구분자 통일, 오타 없음

**결론: 실제 브로커를 붙였을 때 두 서비스가 정상 통신 가능하다.**

교차 검증 과정에서 [5.3](#53-stage-6-발행-insert-순서-레이스-경계면-qa가-찾아낸-실제-버그)의
레이스 버그를 포함해 계약 밖 부수 효과 3건을 찾았다. A(레이스)는 이번 스코프에서 바로
수정했고, B·C는 [10장](#10-향후-과제)으로 넘겼다.

## 10. 향후 과제

경계면 QA와 두 담당자가 각자 남긴 항목을 모았다. 우선순위 순으로 정리했다.

- **`unique_execution_plan_key`에 `user_id` 누락 (선행 버그, Kafka와 무관하지만 시급)**: 라이브
  DB에는 `UNIQUE (execution_date, stock_code, trade_type)` 제약이 존재하는데, **어떤
  Liquibase changeset에도 이 제약이 없다** — v1.0~v1.25 전체를 확인했다. Liquibase 도입 이전
  또는 수동으로 생성된 스키마 드리프트로 보인다. 두 유저가 같은 날 같은 종목/방향을 거래하면
  `trade_execution_plan` INSERT가 통째로 롤백된다(멀티유저 환경에서 실재하는 위험). 이번
  레이스 수정으로 INSERT가 발행 앞으로 당겨지면서, 충돌 시점도 "발행 후"에서 "발행 전"으로
  바뀌었다 — 영향 범위는 같지만 순서가 바뀌었으니 changeset 작성 시 함께 확인 필요.
  `dropUniqueConstraint`에 `preConditions`를 걸어야 한다(환경마다 제약 유무가 다르므로).
- **outbox 패턴 부재**: 결과 발행(`trade.order.result`)이 `trade_history` 원장 기록과 원자적이지
  않다. 지금은 실용적 타협이지만, 트래픽이 늘면 재검토 대상.
- **PENDING/QUEUED 잔여 행 알람 부재**: 결과 메시지가 영영 안 오면(브로커 장애 등) 행이 무한정
  PENDING/QUEUED로 남는다. reconcile 배치나 알람이 없다.
- **DLQ 컨슈머 부재**: `trade.order.dlq`로 격리는 되지만, 이걸 사람이 확인하는 절차/도구가 아직
  없다.
- **`EXECUTED`의 의미가 "KIS 접수"이지 "체결"이 아님**: 시장가 주문은 접수와 체결 사이에 시차가
  있을 수 있는데, 지금 상태값은 이 차이를 구분하지 않는다.
- **`GET /api/trading/recent` 표시 정확도 (frontend-engineer 영역)**: 이제 실제 데이터가
  반환되면서 `HomeView.vue`가 `orderStatus`를 확인하지 않고 무조건 "체결"로 표시하는 문제,
  시장가 주문의 `executedPrice`가 null이라 `orderPrice ?? 0`으로 "체결가 0원"이 뜨는 문제를
  발견했다. 런타임 크래시는 아니지만 사용자에게 잘못된 정보를 보여준다.
- **Gemini 결정 큐잉 (이슈 3, 이번 스코프 제외)**: 당일 컷오프 정책이 확정되면 같은 Kafka
  인프라로 `decision.requested` 토픽을 추가하는 방향을 이미 검토했다.
- **ai-agent 전용 DLQ 부재**: 파이프라인 컨슈머는 핸들러가 실패해도 오프셋을 커밋한다(poison
  메시지가 루프를 영구 정지시키는 걸 막기 위한 의도적 설계). 대신 실패가 조용히 넘어가지 않도록
  DLQ나 별도 알람이 필요하다.
- **오래된 `pipeline.run.requested` staleness 가드 부재**: 컨슈머가 오래 죽어있다 살아나면
  쌓인 메시지를 전부 순차 실행하게 된다. 당일이 지난 트리거는 스킵하는 가드가 없다.
- **실 인프라 end-to-end 미검증**: 두 서비스 각각 Testcontainers로 검증했고 경계면은 정적으로
  교차 확인했지만, `docker compose up` 후 실제로 두 프로세스를 하나의 브로커에 동시에 붙여
  `POST /api/pipeline/trigger`를 실행해보는 진짜 end-to-end 테스트는 아직 하지 않았다. 실 KIS
  모의계좌 크레덴셜로 `ODNO` 추출·`rt_cd` 처리가 실제로 동작하는지도 미검증이다.
