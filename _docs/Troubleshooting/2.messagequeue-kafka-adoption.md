## 1. 문제 정의

ai-agent가 매일 08:50 파이프라인 Stage 6에서 산출한 매수/매도 결정을 api-server에 전달해
KIS 모의투자 주문을 실행하는데, 이 경로에 두 가지 신뢰성 문제가 있었다.

**이슈 1 — 매매 주문 유실.** ai-agent Stage 6이
`POST /api/internal/users/{userId}/trades/{buy|sell}`를 aiohttp로 동기 호출하는데, 실패 시
재시도가 전혀 없었다. api-server가 다운돼 있거나 KIS가 타임아웃되면 그 주문은 영구히 사라지고,
파이프라인 자체는 "성공"으로 마감됐다. 게다가 `TradingService.executeBuy/executeSell`는
`trade_history` 테이블에 아무것도 쓰지 않아서(`TradeHistoryRepository`의 유일한 사용처가 읽기
하나뿐) `GET /api/trading/recent`가 항상 빈 배열을 반환하고 있었다 — 매매 감사 로그가 시스템
어디에도 없었다.

**이슈 2 — 파이프라인 동시 실행 방지 부재.** 평일 08:50 스케줄 트리거와
`POST /api/pipeline/trigger` 수동 트리거가 각각 독립적으로 `PipelineOrchestrator`를 실행할 수
있는데, 동시 실행을 막는 락이 전혀 없었다. 겹치면 같은 날짜 행을 중복 DELETE 후 재삽입하고,
최악의 경우 동일 유저에게 중복 매수 주문이 나갈 수 있었다.

## 2. 왜 Kafka인가

두 이슈 모두 본질은 "요청과 실행을 분리하고, 실행이 실패해도 요청이 사라지지 않게 하는 것"이라
Kafka의 Producer/Consumer 모델과 정확히 맞아떨어진다. 주문 요청을 큐에 발행해두면 소비자(컨슈머)
쪽 장애·지연과 무관하게 요청 자체는 보존되고, 실패 시 재시도·DLQ 격리를 브로커 레벨에서
표준적으로 다룰 수 있다. 파이프라인 트리거도 마찬가지로, 두 진입점(스케줄/수동)을 하나의 토픽에
발행하도록 모으면 단일 컨슈머가 이를 순차 소비하면서 자연스럽게 직렬화된다.

조사 과정에서 Kafka 적용 후보를 5개까지 검토했다(주문 유실, 파이프라인 동시성, Gemini API
호출 큐잉, 종목 단위 수집 재시도, Stage 경계 체크포인트). 이 중 설계가 확정돼 있고 바로
검증 가능한 범위인 **이슈 1·2만 이번에 구현**했다:

- 종목 단위 수집 재시도는 KIS 5req/s 전역 제한이 그대로라 처리량 이득이 없어 이번 스코프에서
  뺐다.
- Stage 경계 체크포인트는 파이프라인 내부 구조(DataFrame을 지역변수로 넘기는 780줄 단일 함수)의
  선행 리팩터링이 필요해 공사 규모가 이번 스코프를 넘었다.
- Gemini 결정 큐잉은 당일 컷오프 정책(큐가 밀렸을 때 처리 기준)이 아직 확정되지 않아 제외했다.

두 이슈는 서로를 보강한다 — 이슈 1에서 만든 멱등키가 이슈 2의 잔여 리스크(파이프라인 중복 실행
시 중복 주문)까지 막아주는 안전망 역할을 한다. 이 관계는 [6장](#6-실측-결과)에서 실측으로
확인한다.

## 3. 메시지 계약 설계

api-server(backend-engineer)와 ai-agent(ai-pipeline-engineer)를 각각 독립적으로 작업시키기
위해, 아래 스펙을 고정 계약으로 먼저 정했다.

| 토픽 | 발행 | 소비 | 용도 |
|---|---|---|---|
| `trade.order.requested` | ai-agent | api-server | 주문 요청. key = `{userId}:{stockCode}:{tradeDate}:{side}`(멱등키) |
| `trade.order.result` | api-server | ai-agent | 처리 결과(`SUCCESS`\|`FAILED`) |
| `trade.order.dlq` | api-server | (운영자 수동 확인) | 재시도 소진/재시도 불가 주문 격리 |
| `pipeline.run.requested` | ai-agent(스케줄+수동) | ai-agent(단일 컨슈머) | 트리거 직렬화 |

메시지 본문은 8개 필드(`idempotencyKey`, `userId`, `stockCode`, `side`, `quantity`, `price`,
`tradeDate`, `requestedAt`)로 고정했고, 멱등키는 record key와 body 양쪽에 모두 채우도록 해서
컨슈머가 어느 쪽을 읽어도 안전하게 만들었다.

## 4. 구현

### 4.1 api-server — 컨슈머, 멱등성, DLQ

**PENDING 선(先) claim.** KIS 호출 *후*에만 결과를 기록하면, 주문 직후 프로세스가 죽었을 때
흔적이 안 남아 재전달 시 이미 나간 주문을 또 낼 위험이 있다. 그래서 KIS 호출 **전에** PENDING
행을 INSERT하고 즉시 커밋(`REQUIRES_NEW`)한다. 행의 **존재 자체**가 재실행을 막는 1차 방어선이고,
2차 방어선은 `trade_history.idempotency_key` UNIQUE 제약이다. Liquibase
`v1.25-trade-history-idempotency.yaml`로 `idempotency_key VARCHAR(120)`(NULL 허용) + UNIQUE
제약을 추가했다 — NULL을 허용해서 기존 행과 비-Kafka 경로(수동 주문/REST)는 이 제약에 걸리지
않는다.

**재시도 경계는 "KIS를 호출했는가"라는 단계(phase) 기준으로 나눴다.** 컨슈머 로직을 3단계로
구분한다:

- **PHASE 0**(메시지 파싱)·**PHASE 2**(KIS 호출 전/후) 실패는 재전달을 원천 차단하고 즉시 FAILED
  확정 + DLQ 격리한다. 시장가 주문에서 KIS 타임아웃은 "안 들어갔다"가 아니라 "들어갔는지
  모른다"는 뜻이라, 여기서 재시도하면 이중 체결 위험이 있기 때문이다.
- **PHASE 1**(DB 커넥션 등 KIS를 아직 안 건드린 인프라 오류)만 Spring Kafka의
  `DefaultErrorHandler` + `ExponentialBackOff`(초기 2초, 배수 2, 최대 3회)로 재시도한다. 소진되면
  커스텀 `ConsumerRecordRecoverer`가 `trade.order.dlq`로 보낸다.

**Kafka JSON serde는 String으로 고정**했다. spring-kafka 4.1(Jackson 2)과 Spring Boot
4.1(Jackson 3)이 공존하는 상태에서 `JsonSerializer`를 그대로 쓰면 직렬화 포맷이 갈릴 위험이
있어, JSON 매핑을 코덱 한 곳으로 모아 통일했다.

### 4.2 ai-agent — 프로듀서/컨슈머, 파이프라인 직렬화

**`messaging/` 패키지 신설.** `pipeline`과 `execution` 양쪽이 이 모듈을 쓰므로 독립 패키지로
뺐다. 기존 `internal_api_client.py`(REST 클라이언트)는 남겨서 디버깅/수동 실행 경로로 계속
쓴다.

**결과 수신 상태 매핑.** 결과 메시지의 `status: "SUCCESS"|"FAILED"`는 와이어 계약 그대로
유지하되, ai-agent 자신의 `trade_execution_plan.execution_status` 컬럼에는
`RESULT_STATUS_TO_DB` 매핑을 거쳐 `EXECUTED`로 저장한다. 기존 뷰 `v_latest_trade_plan`,
`v_market_overview`가 `execution_status = 'EXECUTED'`로 체결 건수를 세고 있어서, `SUCCESS`를
그대로 넣으면 대시보드 집계가 조용히 0이 되기 때문이다. 원문 status는 `execution_result`
JSONB에 그대로 보존한다.

**파이프라인 직렬화**는 스케줄·수동 트리거 둘 다 `PipelineOrchestrator`를 직접 호출하지 않고
`pipeline.run.requested`(key=trade_date, 파티션 1개)에 발행하도록 바꿨다. 단일 컨슈머가 이
토픽을 순차 소비해 실제 `run_complete_pipeline()`을 실행한다. 수동 트리거 엔드포인트는 발행 직후
즉시 202를 반환한다(이전엔 파이프라인 전체가 끝날 때까지 동기 대기).

**검증 과정에서 발행-INSERT 순서 레이스를 하나 발견해 고쳤다.** 처음 구현은 "① Kafka 발행 →
② `trade_execution_plan` 배치 INSERT" 순서였는데, api-server가 KIS를 호출하지 않고 즉시 실패를
반환하는 초고속 경로에서는 결과가 INSERT보다 먼저 도착해, 이미 확정된 실패가 나중에 온 배치
INSERT로 `QUEUED`에 덮여버리는 경우가 있었다. 순서를 "① 초기 레코드(QUEUED) INSERT → ② 그
다음 발행 → ③ 발행 자체가 실패한 주문만 단건 UPDATE"로 뒤집어, 결과가 도착할 수 있는 시점보다
행이 항상 먼저 존재하도록 고쳤다. 이 레이스를 재현하는 테스트 5개를 작성해 수정 전 전부 실패,
수정 후 전부 통과하는 걸 확인했다.

## 5. 검증 (TDD)

Testcontainers로 실제 인프라(Kafka + PostgreSQL)를 띄워 프로덕션 코드 경로를 그대로 검증했다.

### api-server (`kafkaTest` 태그, Docker 필요해 기본 `test`에서 분리)

실제 PostgreSQL(TimescaleDB)+Kafka(`apache/kafka:4.0.0`, KRaft) 컨테이너에 전체 Liquibase
changelog를 적용, KIS 클라이언트만 목으로 대체.

| 테스트 | 검증 항목 | 결과 |
|---|---|---|
| 정상 매수/매도 주문 | `EXECUTED` 기록 + result `SUCCESS` 발행 | PASS |
| 동일 키 3회 발행 | KIS 호출이 **정확히 1번**만 일어남(멱등성) | PASS |
| KIS 타임아웃 | 재시도 없이 즉시 DLQ(claim 1회, retryCount:0) | PASS |
| KIS 비즈니스 오류(4xx) | 재시도 없이 즉시 DLQ | PASS |
| 인프라 레벨 일시 오류 | claim 4회(최초1+재시도3), retryCount:3, **KIS 호출 0회** | PASS |
| 계약 위반 메시지 | DLQ 격리, KIS 0회 | PASS |

**7개 전부 통과**(12.7s). 회귀: `./gradlew test` **491개 전부 통과**(Kafka 테스트는 별도 태그로
분리해 영향 없음). `timescaledbTest` 17개도 v1.25 changeset 추가 후 정상 적용.

### ai-agent (`pytest`, venv 내 실행)

로컬 Kafka 컨테이너 + 실 PostgreSQL로 (a) 트리거 즉시 응답, (b) 스케줄+수동 트리거 동시 발생 시
직렬 처리, (c) 발행 메시지가 계약 스키마와 정확히 일치, (d) 결과 수신 시 `trade_execution_plan`
갱신을 검증. 발행-INSERT 순서 레이스 수정 후 이를 재현하는 `TestFastResultRace` 5개를 추가.

회귀: **740 → 864 passed, 0 failed**(Kafka 프로듀서/컨슈머 +110, 레이스 수정 +20/−6).
`messaging/` 패키지 커버리지 90~100%, `pipeline/orchestrator.py` 99%, 전체 TOTAL 92%.

### 병합 후 독립 재검증

api-server·ai-agent 각각 격리된 작업 환경에서 구현한 뒤 병합했고, 병합된 트리에서 두 스위트를
다시 돌려 동일한 결과가 재현되는지 확인했다 — api-server 491+7, ai-agent 864, 전부 재현.

## 6. 실측 결과

### 6.1 트리거 응답 시간

가짜 파이프라인(2,000ms 시뮬레이션) 기준, 수동 트리거 3회 실측:

| 상황 | 응답 시간 |
|---|---|
| 유휴 시 트리거 | 32.4ms / 3.6ms / 3.9ms |
| **파이프라인 실행 중** 트리거 | **13.6ms / 7.6ms / 10.8ms** |

이전엔 파이프라인 전체(수십 분)가 끝날 때까지 동기 대기했던 것과 비교하면, 발행 후 즉시 응답하는
구조로 확실히 바뀌었다.

### 6.2 파이프라인 직렬화

`_job_wrapper()`를 실제 별도 스레드에서 호출하며 동시에 HTTP로 수동 트리거를 걸어 측정:

```
run2 시작 - run1 종료 = +0.028s / +0.008s / +0.005s   (3연발 반복 동일)
최대 동시 실행 수 = 1 (한 번도 2가 된 적 없음)
```

항상 양수 — 겹치지 않고 순차 실행됨을 확인했다. 두 요청 모두 유실 없이 큐에 쌓여 순서대로
실행됐다.

### 6.3 멱등성이 파이프라인 중복 실행의 잔여 리스크를 막아주는가

2장에서 세운 설계 의도("이슈 1의 멱등키가 이슈 2의 잔여 리스크도 막아준다")를 실측으로
확인했다. 같은 거래일로 파이프라인을 두 번 실행하면 ai-agent는 메시지 **2건**을 발행하지만(두
키는 완전히 동일), api-server의 멱등성 계층을 거치면 실제 실행은 **1건**으로 줄어든다 — 즉
"분석 단계는 중복으로 돌아도 실제 주문은 한 번만 나간다"는 설계 의도가 실측으로 성립함을
확인했다.

멱등키에 수량은 포함하지 않았다 — 재실행 사이에 계획 수량이 바뀌어도(예: 10주→50주) 먼저
도착한 요청이 이기는 것이 의도된 동작이다.

## 7. 경계면 교차 검증

api-server·ai-agent가 독립적으로 구현했으므로, 실제로 같은 메시지 포맷을 주고받는지 정적
대조로 확인했다. ai-agent의 실제 직렬화 코드를 실행해 나온 바이트를 api-server DTO/테스트
픽스처와 직접 비교하는 방식이다.

**7개 계약 항목 전부 일치**:

1. `idempotencyKey`가 record key와 body 양쪽에 모두 채워짐
2. 멱등키 조합 규칙 — api-server가 키를 재조립하지 않고 받은 문자열을 그대로 저장/반환
3. JSON 필드명 camelCase 통일
4. `status` 값은 wire 상 그대로 유지되고, `EXECUTED` 매핑은 ai-agent DB 저장 시점에만 적용
5. `price`/`quantity` 타입 일치, 시장가 `price=0`의 의미도 양쪽에서 동일
6. 타임스탬프 — `requestedAt`은 오프셋 포함 ISO-8601로 양쪽 파싱 가능
7. 토픽 이름 — 점 구분자 통일, 오타 없음

**결론: 실제 브로커를 붙였을 때 두 서비스가 정상 통신 가능하다.**

## 8. 최종 결과

- **구현 완료**: `trade.order.requested`/`trade.order.result`/`trade.order.dlq`(매매 주문
  신뢰성), `pipeline.run.requested`(파이프라인 직렬화)
- **인프라**: `docker-compose.yml`에 Kafka(`apache/kafka:4.0.0`, KRaft 단일 노드) 추가
- **스키마**: `v1.25-trade-history-idempotency.yaml` — `trade_history.idempotency_key`
  VARCHAR(120) NULL 허용 + UNIQUE
- **멱등성**: 동일 메시지 3회 발행해도 KIS 호출 1회로 검증(PENDING 선점 + DB UNIQUE 이중 방어)
- **재시도/DLQ**: KIS 호출 여부를 기준으로 재시도 가능/불가를 구분 — 도달 불확실 실패와 명시적
  거부는 즉시 DLQ, 인프라 레벨 일시 오류만 지수 백오프 재시도 후 DLQ
- **응답성**: 파이프라인 트리거가 동기 대기(수십 분)에서 발행 후 즉시 응답(수 ms~30ms)으로 전환
- **동시 실행 방지**: 실측상 항상 직렬 처리, 요청 유실 없이 큐잉
- **회귀**: api-server 491개(+ Kafka 전용 7개) + ai-agent 740→864개, 전부 통과
- **경계면**: 7개 계약 항목 전부 일치, 정적 교차 검증 통과

## 9. 향후 과제

- **outbox 패턴 부재**: 결과 발행(`trade.order.result`)이 `trade_history` 원장 기록과 원자적이지
  않다. 지금은 실용적 타협이지만, 트래픽이 늘면 재검토 대상.
- **PENDING/QUEUED 잔여 행 알람 부재**: 결과 메시지가 영영 안 오면(브로커 장애 등) 행이 무한정
  PENDING/QUEUED로 남는다. reconcile 배치나 알람이 없다.
- **DLQ 컨슈머 부재**: `trade.order.dlq`로 격리는 되지만, 이걸 사람이 확인하는 절차/도구가 아직
  없다.
- **`EXECUTED`의 의미가 "KIS 접수"이지 "체결"이 아님**: 시장가 주문은 접수와 체결 사이에 시차가
  있을 수 있는데, 지금 상태값은 이 차이를 구분하지 않는다.
- **Gemini 결정 큐잉 (이슈 3, 이번 스코프 제외)**: 당일 컷오프 정책이 확정되면 같은 Kafka
  인프라로 `decision.requested` 토픽을 추가하는 방향을 검토했다.
- **ai-agent 전용 DLQ 부재**: 파이프라인 컨슈머는 핸들러가 실패해도 오프셋을 커밋한다(poison
  메시지가 루프를 영구 정지시키는 걸 막기 위한 의도적 설계). 대신 실패가 조용히 넘어가지 않도록
  DLQ나 별도 알람이 필요하다.
- **오래된 `pipeline.run.requested` staleness 가드 부재**: 컨슈머가 오래 죽어있다 살아나면
  쌓인 메시지를 전부 순차 실행하게 된다. 당일이 지난 트리거는 스킵하는 가드가 없다.
- **실 인프라 end-to-end 미검증**: 두 서비스 각각 Testcontainers로 검증했고 경계면은 정적으로
  교차 확인했지만, `docker compose up` 후 실제로 두 프로세스를 하나의 브로커에 동시에 붙여
  `POST /api/pipeline/trigger`를 실행해보는 end-to-end 테스트는 아직 하지 않았다. 실 KIS
  모의계좌 크레덴셜로 `ODNO` 추출·`rt_cd` 처리가 실제로 동작하는지도 미검증이다.
